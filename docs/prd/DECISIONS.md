## Valen P0 coverage integration

The authorized SC-14 implementation distinguishes an absent category in processed documents (`NOT_OWNED`, explicitly “tidak ditemukan di dokumen”) from pending/unknown evidence (`NEEDS_CHECK`). Neither is an exclusion. An actual exclusion requires a reviewed negative benefit plus an exact owned retained-page quote that names the category and supports exclusion. Required needs additionally need checked official-source metadata. Account SC-04 now uses the same visa service as SC-14 when normalized policies exist; its legacy manual-only path uses the same inclusive interval core. Existing data and API shapes are preserved; CoverageNeed receives additive evidence/context fields.
# Valen P0 contract activation (19 October 2026)

The authorized implementation activates canonical home, Q&A, pathway comparison, coverage-needs and **case creation only** for existing bearer accounts or demo sessions. It does not activate triage/emergency UI, claim checklist/evidence/submission, reminders or action execution. Request/response changes are additive and generated from Python; original required PRD fields remain present. See `docs/agent-tasks/valen/INTEGRATION.md` for transport and source boundaries.

Creating a DRAFT adds optional `comparison_id` to the wire schema and an `Idempotency-Key` header. The live service requires both after owned-coverage validation (409 COMPARISON_REQUIRED / 422 IDEMPOTENCY_KEY_REQUIRED when absent). This intentionally strengthens the old contract-only operation: no working 2xx consumer existed. The owned comparison binds current context and policy/KB evidence for 15 minutes; one comparison and one actor/key can create only one canonical payload. Identical retries return the original ID, conflicting choices return 409. This prevents forged paths and duplicate cases across workers. Claim checklist/detail APIs remain their existing contracts, including their current demo-only/501 limitations.

Q&A uses JSON or named SSE, with additive progress, chat IDs, per-policy numeric facts and verification steps. Helpers under `/ask` scope history, feedback and original pages to the existing actor. No second authentication or parallel unversioned API was added. Account retention revocation and document/data deletion invalidate derived source/history content. The coverage and pathway readers consume existing coverage-linked reviewed fields; there is no duplicate benefits authority.
