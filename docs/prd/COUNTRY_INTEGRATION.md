## Profile edits and original records

The active `UserProfile.country_code` selects the country KB on each assessment request. It is not the origin of every owned policy/document. `UnifiedInsuranceRecord.country_code` remains the origin of the existing seeded record, including its policies/document summaries. Persisted `DocumentRow.country_code` is independent and also remains unchanged. A profile PUT must never rewrite those countries, IDs, source references, values, currencies or insurance dates, or delete records. `owned_coverage` is self-reported profile metadata, not an instruction to relabel policies.

On a country change, omitted city, timezone, institution_name, arrival_date, visa_expiry_date, budget_range and currency are cleared to null in the profile. They cannot silently inherit a previous country's residence/visa/budget context. Explicit destination values in the same PUT are accepted under existing validation; same-country partial updates retain omitted fields. Identity, occupation/employment, dependents, priorities and self-reported owned_coverage remain intact. Validation and KB support checks precede persistence; failed changes are atomic. The existing single PROFILE_UPDATED audit event and independent consent grants remain unchanged; raw profile values are not logged. No migration is needed for existing nullable JSON fields.

The current visa endpoint has no persisted assessment cache: each call reads the current profile and original record. If their country codes differ, return NEEDS_VERIFICATION with null gap_days, empty gap_periods and an explicit origin/current-country explanation, even if the new KB has no matching visa rule. `applicable` still describes whether the current KB has a matching rule; false **does not** override NEEDS_VERIFICATION into a successful/non-applicable assessment. Existing UI uses assessment_status to distinguish that uncertainty from NOT_APPLICABLE, and labels seeded policies/documents with the record's country. Matching-country Sinta still returns NOT_APPLICABLE; matching-country Raka with explicit dates still yields 76 potential days, never a legal finding. After AU→ID→AU without new dates, the old 76-day result must not revive.

Current aggregate contracts describe one origin per seeded insurance record; they do not represent arbitrary mixed-country policies/documents in one aggregate. A future mixed-country contract requires an explicit reviewed extension with per-object origin and territorial evidence. Never stamp all imported objects with the active profile country to bypass that limitation, and never treat matching country alone as proof of coverage.

There is no profile editor in the demo. The future US-02-02 wizard must present the required context-change confirmation and require destination details, then invalidate/reload profile, assessment and country-derived views together. Do not merge the returned profile alone into a cache retaining the previous assessment; guard in-flight responses against later edits. Current session restoration/full-page reload fetches current backend data; it is not a live cross-tab subscription or an atomic multi-endpoint snapshot. Document/country labels come from the record, never from a new profile badge. Completing that wizard, client cache coordination and mixed-country ingestion remains outside this pass.
